## G-27 — PIHD-клиент, отдача сегментов и fallback

**Новая цель владельца:** реализовать и проверить клиентскую часть как
экспериментальное расширение, с безопасным переходом на обычный header sync;
это не обязательное требование совместимости с релизом Rust v5.5.2. По
просьбе владельца в план также включена серверная отдача header-сегментов,
необходимая для честного объявления capability. **Статус PARTIAL / live NOT VERIFIED.**

**Что уже видно в коде:** `PihdClient` и сообщения 29/30, режим `off` по
умолчанию, последовательные запросы, привязка ответа к connection/peer и пути
возврата на legacy; `full` сейчас трактуется как `client`, серверной выдачи нет.
Это чтение кода и исторические тесты, а не подтверждение рабочего межсетевого
цикла. Источник и ограничения: [PIHD_UPSTREAM](PIHD_UPSTREAM.md), раздел 8.

**Установлено по Rust staging `83ff9af346faffe711aefb6b3c292308d261eec3`:**
сервер игнорирует `GetHeaderSegment`, если у запрашивающего нет `PIHD_HIST`;
описание бита означает возможность предоставлять исторические сегменты.
Текущий C++ не объявляет бит и не отдаёт сегменты. Для честной совместимости
нужна готовая серверная отдача до рекламы бита. Это статическая проверка кода;
двусторонний live-обмен ещё NOT VERIFIED. [Rust protocol](https://github.com/mimblewimble/grin/blob/83ff9af346faffe711aefb6b3c292308d261eec3/p2p/src/protocol.rs#L196-L215),
[Rust capability](https://github.com/mimblewimble/grin/blob/83ff9af346faffe711aefb6b3c292308d261eec3/p2p/src/types.rs#L552-L556).

   capability/handshake и семантику client-only; сверить арифметику сегментов,

## G-27 — подробный план серверной части PIHD

**Цель и приоритет.** По запросу владельца дополнить существующий клиент
сервером детерминированных сегментов **заголовков**. Это экспериментальное
расширение сверх Rust v5.5.2, не часть PIBD-архива или консенсуса. До
подтверждения и отдельного решения о включении — default `off`; работа не
вытесняет критичные G-09/recovery/NRD. Статусы: реализация **OPEN**,
совместимость C++/Rust staging на проводе **NOT VERIFIED**.

**Зафиксированный эталон:** Rust staging commit
[`83ff9af346faffe711aefb6b3c292308d261eec3`](https://github.com/mimblewimble/grin/tree/83ff9af346faffe711aefb6b3c292308d261eec3).
В дальнейшем перед реализацией перепроверить выбранный commit и записать его,
не подменяя приёмку ссылкой на движущуюся ветку. В проверенном срезе Rust:

- отклоняет запрос без `PIHD_HIST` у запрашивающего и при неверной высоте ID;
- использует `height=9`, вместимость 512, `start = idx * 512 + 1` с checked
  arithmetic; диапазон заканчивается на min(start + 511, header head);
- отдаёт `HeaderSegment` с исходным ID и `u16` количеством заголовков;
  запрос за пределом head может получить пустой список;
- применяет ограничение **500 запросов / 60 с** по адресу. Прежние 120/60 в
  `PIHD_UPSTREAM.md` — устаревшее значение для этого commit. Для C++ разумный
  лимит подобрать и измерить; точное копирование не является обязательным.

Исходники: [Rust protocol](https://github.com/mimblewimble/grin/blob/83ff9af346faffe711aefb6b3c292308d261eec3/p2p/src/protocol.rs#L196-L215),
[Rust serving](https://github.com/mimblewimble/grin/blob/83ff9af346faffe711aefb6b3c292308d261eec3/servers/src/common/adapters.rs#L389-L444),
[формат ответа](https://github.com/mimblewimble/grin/blob/83ff9af346faffe711aefb6b3c292308d261eec3/p2p/src/msg.rs#L657-L693).

### 1. Контракт режимов и capability

1. Согласовать явные режимы конфигурации и переходы. Существующее поведение:
   `off` по умолчанию; `full` сейчас разбирается как client, не сервер. Не
   называть это текущей реализацией full и не менять значение прежних настроек
   молча. Предпочтительный целевой `full` включает клиент и сервер только после
   их готовности; политика клиентского режима без честного capability должна
   быть явно описана. Выключение и повторное включение через локальный owner API во время работы —
   требования владельца; детали и границы — в разделе 1.1 ниже.
2. Найти все места формирования Hand/Shake и capability для inbound/outbound;
   при выключенном или неготовом сервере `PIHD_HIST` не объявлять. Объявление
   бита возможно только если служба может ответить на запросы по имеющейся
   валидированной header-цепочке; не требовать полной body/PIBD-синхронизации,
   если это не обосновано контрактом.
3. Handshake фиксирует возможности соединения: отдельно спроектировать
   выключение/потерю готовности при уже объявленном бите. Не предполагать, что
   изменение локального флага меняет capability на открытом соединении. Выбрать
   безопасную политику для существующих соединений и проверить её; если нужен
   reconnect, делать его ограниченно и без массовых разрывов. Ошибки локального
   хранения не превращать в ложное сообщение о нарушении peer.

### 1.1. Локальное выключение и включение PIHD через owner API

**Требование владельца:** при работающем процессе дать владельцу возможность
выключить и снова включить экспериментальный PIHD через локальный API, без
перезапуска ноды. Операции охватывают клиентские запросы и серверную выдачу. Это запланированная
возможность, а не утверждение о готовом endpoint. `off` остаётся default.

1. Использовать отдельный административный метод существующего `/v2/owner`
   или столь же узкий локальный интерфейс; не добавлять изменение режима на
   `/v2/foreign` и не полагаться на имя маршрута. Изучить фактическую систему
   `ApiAccess` и интеграцию сервера на момент реализации: текущие
   `UpdateConfigHandler` и уровни доступа — только отправная точка, их наличие
   не доказывает, что конкретный новый метод защищён. Изменение — только с
   административной аутентификацией и разрешением владельца процесса, fail
   closed при отсутствующих/ошибочных credentials или настройках прав.
2. Принимать управление исключительно локально: убедиться в фактическом адресе
   bind и source peer для IPv4/IPv6, исключить проксирование и обход через
   заголовки. Loopback сам по себе не подтверждает владельца: секрет доказывает
   владение секретом, а не автоматически личность OS-пользователя. Защитить
   credential и файлы конфигурации правами текущего владельца; если требуется
   строгая проверка OS-учётной записи, проверить поддерживаемый механизм
   локальной IPC-аутентификации/DACL. Не заявлять более сильную гарантию, чем
   обеспечивает выбранный и проверенный механизм.
3. Поддержать команды `disable`, `enable` и чтение состояния; конкретные имена
   RPC и формат — при проектировании, с обратной совместимостью. Возвращать
   понятное состояние `enabled/disabled`, готовность сервера, режим и результат
   выключения. Разграничить запрошенный режим, фактически действующее состояние
   и уже согласованные в handshake возможности. Повторные команды идемпотентны.
4. Определить одно атомарное runtime-состояние и порядок остановки: запретить
   новые клиентские запросы и новые серверные операции, отменить/завершить
   ожидающие в ограниченное время, игнорировать запоздалые ответы и передать
   header sync в legacy без потери подтверждённого прогресса. Не прекращать
   обработку P2P в целом и не банить peer из-за локального выключения. Проверить
   гонки между командой, выдачей, read lease, соединением и callback.
5. Capability согласуется при handshake. Не утверждать, что уже подключённые
   peers мгновенно увидят снятие `PIHD_HIST`: определить ограниченную политику
   завершения/переустановления затронутых соединений либо иной безопасный режим,
   который не обещает бесконечную выдачу после выключения. В API отразить
   `disabling`/`disabled` или эквивалент до фактического завершения перехода;
   не возвращать успешное окончательное выключение раньше выполнения контракта.
6. Явно согласовать и задокументировать сохранение настройки между рестартами:
   первая версия — runtime-only, как определено ниже. Не перезаписывать чужие
   config и не обещать persistent disable без отдельной реализации; при
   неизвестном/повреждённом состоянии безопасный default — `off`. Повторное
   включение после owner `disable` — только отдельной защищённой командой
   владельца. Если owner оставил режим включённым, сетевая повторная попытка
   после временного fallback/cooldown допустима: это не owner-`enable` и не
   отменяет явное выключение.
7. Минимальные проверки: локальный владелец может отключить PIHD в середине
   загрузки и выдачи, legacy sync продолжает работу; неподтверждённый,
   удалённый, foreign и неверно авторизованный запрос ничего не меняет;
   проверить IPv4/IPv6, доверие proxy, защиту секретов, параллельные и повторные
   команды, незавершённый ответ, активные соединения, возможный restart и
   итоговые рекламируемые capability. Проверить, что секреты не попадают в логи
   и ответы. Проверки безопасного включения описаны ниже. Unit и API integration
   — отдельно от live Rust fallback.

**Единый контракт переходов (аудиторская сверка 03.11.2026).**

- Не смешивать четыре независимые величины: `desired` владельца (`off/on`),
  состояние локального сервера и его readiness, фактический sync mode
  (`legacy/PIHD`) и capability, объявленный конкретному соединению. `on + ready`
  без PIHD-peer — нормальное состояние: активен legacy, сервер доступен, ждать
  peer; это не отказ включения и не live PASS. Если сеть отказала при `desired=on`,
  разрешены bounded retry/cooldown; после owner `disable` автоматический retry и
  любое повторное включение запрещены до нового разрешённого `enable`.
- Для первой версии runtime-команды не меняют конфигурационные файлы. При новом
  запуске применяется явно заданная конфигурация, иначе `off`; результат API
  прямо указывает `runtime_only` и что он не переживает restart. Не писать
  устойчивый `on` автоматически. Если впоследствии понадобится постоянное
  переключение — отдельный opt-in контракт и тесты; предыдущая рекомендация
  «согласовать runtime или persistence» заменяется этим выбором для первой версии.
- `enable` включает запрошенный полный режим client+server, а не только клиент;
  отдельный режим без serving не рекламирует `PIHD_HIST` и не считается рабочим
  клиентом против закреплённого Rust staging. Старое значение config `full`,
  сегодня эквивалентное `client`, мигрировать явно с диагностикой и тестом,
  не менять смысл установленной настройки незаметно. До готовности нового full
  текущий режим и результаты не считать реализованными.
- Для `disable` зафиксировать конечный deadline и контракт: после команды не
  принимать новые PIHD-работы; уже начатые работы ограниченно завершаются либо
  отменяются. Соединения, которым мы уже обещали `PIHD_HIST`, должны быть
  завершены адресно до итогового `disabled`, если иного проверенного способа
  отозвать обещание нет; не отключать peers без этой необходимости. При
  недостижимости дедлайна показывать переход/ошибку и повторять безопасную
  очистку, а не сообщать ложный успешный `disabled`. Legacy и остальные P2P
  сервисы сохраняются.
- Для гонки Hand/Shake и `disable`: capability, зафиксированная в конкретном
  handshake, привязывается к версии/эпохе runtime-состояния; соединение,
  успевшее объявить устаревший бит, учитывается при выключении и не ускользает
  из очистки. Проверять в обеих направлениях соединения и при send-in-flight.
  Ограниченное завершение существующих обещаний и факт, что новые соединения не
  рекламируют бит, — части одного критерия завершённого выключения.
- `enable` не обязан принудительно переподключать peers: сначала сервер ready,
  потом capability объявляется в новых handshake; старые соединения не меняются.
  Следить, чтобы активный legacy sync не конкурировал с PIHD за применение одних
  заголовков; при смене режима сохранить подтверждённый head. При отказе
  readiness, выключении в процессе enable или утрате готовности не публиковать
  устаревший `enabled`; переход разрешать только актуальной операции.
- Owner API: проверять реальный локальный transport/address и admin доступ, а
  не доверять заголовкам. Для HTTP отдельно проверить browser-origin/CSRF,
  DNS-rebinding/Host и поведение reverse proxy согласно архитектуре; отсутствие
  защиты не считать доказанным до проверки. Секрет в журнал/ответы не выводить.
  При отсутствии возможности достоверно ограничить owner-only доступ — fail
  closed для управления PIHD.

**Повторное включение через тот же локальный owner API:**

1. `enable` требует тех же локальных и административных проверок, что и
   `disable`. Метод и имена здесь условные; реализовать через единый управляемый
   state machine, без отдельного незащищённого обходного маршрута. Команда
   задаёт желаемое состояние, но ответ не должен утверждать, что PIHD работает,
   до завершения проверок и перехода.
2. Перед включением проверить инициализацию P2P и сервера, работоспособность
   ограничителей, доступность и согласованность header-chain/read view, корректную
   конфигурацию и отсутствие остановки или recovery. Уточнить минимальные
   readiness-инварианты по фактической архитектуре; не требовать полного PIBD или
   наличия подключённого PIHD peer, если они не нужны для безопасной отдачи.
   Наличие подходящего peer — отдельное условие фактической клиентской работы.
   При отказе или исключении оставить эффективное состояние `off` и legacy sync;
   вернуть причину без секретов, не рекламировать capability.
3. Применять переход атомарно относительно `disable`, новых соединений,
   обработчиков ответов и отправки. Отражать состояние `enabling`, затем
   `enabled/ready` либо `disabled/error`; API должен различать принятие команды и
   фактическую готовность. Повторный `enable` идемпотентен. При конфликтующих
   запросах и остановке процесса определить однозначный порядок; `disable` не
   должен быть потерян из-за запоздалого завершения readiness-check.
4. `PIHD_HIST` включать в handshake только после готовности сервера и возможности
   отвечать. Существующие соединения сохраняют ранее согласованные capability:
   не предполагать мгновенного обновления и не рвать их массово. Определить
   ограниченную политику reconnect/ожидания естественных новых соединений;
   реальную доступность peer и активный PIHD-поток показывать отдельно от
   включённой опции. До подходящего peer продолжать legacy sync.
5. Оговорить дальнейшее состояние после утраты готовности: прекратить новые
   PIHD-операции и безопасно вернуться на legacy, без ложного бана; статус и
   причина должны быть видимы владельцу. Устойчивость настройки через restart
   для первой версии runtime-only по общей политике пункта 6 выше; после
   restart применяется startup config, иначе `off`.
6. Приёмка: `off → enable → ready → disable → enable` без перезапуска; запросы
   без авторизации/с foreign/не локальные отклоняются. Покрыть failed readiness,
   одновременно пришедшие enable/disable, остановку/reorg в процессе включения,
   отсутствие PIHD peer, повторные команды, новые и старые handshake. На live
   Rust staging отдельно подтвердить появление capability на новом соединении,
   работу сервера и клиента и переход на legacy при отказе peer. Не считать
   включение настройки или unit-тест доказательством живого PIHD.

### 2. Обработка запроса и границы

1. В `MessageProcessor.cpp` вместо текущего игнорирования запроса использовать
   проверенный разбор `GetHeaderSegmentMessage` и сервис выдачи; сначала
   проверить режим/готовность, capability peer и лимиты, затем вычислять диапазон.
   Использовать уже существующие классы сообщений и корректную сетевую версию
   сериализации; не добавлять конфликтующие ID.
2. Требовать ID высоты 9; проверять умножение и сложение до вычисления. Генезис
   не отправляется: idx 0 → 1…512, idx 1 → 513…1024. Максимум 512 заголовков,
   тот же ID в ответе. Проверить нулевой head, неполный последний сегмент,
   диапазон полностью за head, `UINT64_MAX`, неверную высоту и повреждённое тело.
   Отказ/пустой ответ согласовать с закреплённым Rust; не отправлять частичный
   произвольный ответ при локальном повреждении или недоступности данных.
3. Если индексы, цепочка или DB неполны — fail closed с ограниченной
   диагностикой. Не возвращать заголовки другой ветки, значения по умолчанию или
   тело блока вместо header. Не считать локальный отказ основанием для бана peer.

### 3. Согласованный header snapshot и reorg

1. Ввести или использовать **один согласованный read view**: header head и все
   записи диапазона должны относиться к одной candidate/header-цепочке. В
   текущем `BlockChain::GetBlockHeaderByHeight` блокировка берётся на каждый
   отдельный вызов, поэтому 512 отдельных вызовов сами по себе не обеспечивают
   один view. Изучить порядок существующих locks, срок жизни указателей и
   гарантии DB до выбора API. Проверить соответствие C++ candidate/header head
   именно `header_head` Rust.
2. Предпочесть короткое получение immutable заголовков в пределах одного read
   lease; сеть и сериализацию выполнять после его освобождения. Альтернатива —
   доказуемый version/hash check с ограниченным retry; при повторной смене
   состояния без ответа. Одна проверка только высоты недостаточна при reorg на
   той же высоте. Не удерживать глобальную блокировку при отправке peer.
3. Проверить последовательность heights и previous-hash соседних заголовков;
   согласовать поведение при нехватке записи. При reorg и закрытии/перезапуске
   БД ответ должен быть целиком старого или целиком нового snapshot либо не
   отправляться. Cache сегментов в первой версии не обязателен: если вводится,
   ключ/инвалидация должны учитывать identity цепочки, включая same-height reorg.

### 4. Ресурсы и отказоустойчивость

1. До чтения ограничить запросы на peer/IP с монотонным временем; дополнительно
   ограничить общий in-flight и общую память очередей/ответов. Множество адресов
   не должно приводить к неограниченной map или накоплению задач. Уточнить уже
   существующие общие P2P-лимиты и не считать per-connection лимит защитой от
   множества соединений.
2. При превышении или перегрузке — ограниченный отказ без выделения больших
   буферов, без блокировки остальных служб и без автоматического бана. Проверить
   малый лимит, одновременных peers, disconnect во время отправки, slow reader,
   остановку сервера, повторное соединение и скачок системных часов.
3. Логировать тип отказа и счётчики без полного содержимого заголовков и без
   спама; метрики запросов, отказов, latency и памяти — достаточны для оценки.

### 5. Клиент и fallback при включении full

1. Проверить наличие работающего источника PIHD, timeout/disconnect, повторные и
   запоздалые ответы, привязку ID/peer/connection, переход на legacy и возврат
   после cooldown. При невалидной цепочке использовать штатную проверку
   заголовков; не принимать их только потому, что ответил PIHD peer.
2. Проверить проблему пустого ответа: Rust при запросе за head может отправить
   `0 headers`, а текущий `PihdClient::OnHeaderSegment` относит пустой список к
   `BanAndFailLocked`. Смоделировать изменение head/stale peer height/reorg;
   если подтверждается легитимность, обеспечить безопасный fallback без ложного
   бана. Это **аудиторская гипотеза**, не подтверждённый live-инцидент.
3. Убедиться, что выключенная функция и fallback с Rust v5.5.2 продолжают работать
   обычным header sync. Сервер и клиент не должны обещать поддержку до готовности.

### 6. Тесты и доказательства приёмки

- **Unit/интеграция:** таблица границ ID/height/overflow и сериализации; capability
  есть/нет, ready/not-ready, неполный и пустой диапазон; локальная missing DB
  запись; проверки лимитов и ошибок без бана. Тестировать и входящий, и исходящий
  handshake, изменение режима и restart; `/W4 /WX` сохранить.
- **Конкурентность:** детерминированный барьер в середине чтения и контролируемый
  reorg, в том числе одинаковая высота с другим hash; assert — ответ одной ветки
  или отсутствие ответа. Проверить остановку/перезапуск и гонки готовности.
- **Негативные wire:** неправильный ID, чужой/поздний ответ, malformed/oversize,
  timeout, отказ сервиса и отсутствие PIHD-пира; никаких ложных банов из-за
  неполного данных или локальных ошибок. Физически недопустимый ответ оценивается
  по действующей политике протокола, а не автоматически приравнивается к timeout.
- **Живой Rust staging:** зафиксировать commit, SHA обоих бинарников, configs,
  изолированные каталоги и logs. Сначала Rust-клиент реально запрашивает PIHD у
  C++-сервера, проверяется правильный ID/диапазон/последовательность и принятие
  заголовков до общего tip/hash. Затем C++-клиент получает сегменты от Rust;
  проверить реальный fallback на legacy при отключении PIHD peer и восстановление.
  Указать, был ли источник состояния fixture, loopback или публичная сеть.
- **Отчёт:** отдельно PASS/FAIL/NOT VERIFIED для unit, controlled reorg,
  нагрузочного теста, live wire, fallback и публичной сети. Прогон только одного
  направления или переход на legacy не является PASS полного PIHD. Если
  доступного staging-пира/данных нет — BLOCKED с причиной, unit не заменяет live.

**Стоп-условие:** после выполнения согласованного контракта, достаточных
регрессионных и двухсторонних live-проверок закрыть задачу в её пределах;
параллельная очередь, сложный cache и новые расширения необязательны без
измеренной потребности. Оценка — несколько рабочих дней как ориентир, зависит
от snapshot API и живого staging-стенда; не обещание срока.

   с аутентификацией и проверкой доступа. Не выставлять wallet owner наружу.
4. Протокол Flint messenger envelope — отдельный прикладной протокол. Не заявлять
   совместимость чата со всеми Grin-кошельками только из-за общего Slatepack или
   onion-адреса. Поддержку конкретных peer/relay версий проверить отдельно.

### Этапы и поведение

1. **Интеграционный контракт.** Разделить UI, messenger service и C++ wallet:
   identity/session, контакты, inbox/outbox, состояние Tor и статусы операций;
   определить локальные методы и ошибки, ownership, ограничение размеров,
   сериализацию версий и запрет секретов в renderer, логах и IPC. Проверить
   реакцию на lock/unlock, смену профиля, смену сети/адреса, остановку wallet и
   restart. Режим testnet и изолированные каталоги — для всей разработки/приёмки.
2. **Tor и сообщения.** Статус bootstrap/onion, start/stop, контакты,
   зашифрованный обмен и отдельные состояния queued/delivered/failed. Direct
   onion требует онлайн-получателя; offline relay — отдельный выбранный транспорт.
   Не обещать анонимность метаданных или forward secrecy, если их нет. Повтор
   доставки использует устойчивый ID, не создаёт новую денежную операцию; ACK и
   подтверждение в блокчейне — разные события. Ограничить payload, TTL и нагрузку.
3. **Slatepack и UI.** Сначала ручной S1→S2→finalize→post с показом суммы,
   комиссии, адреса и результата. Затем opt-in автообработка входящего S1 только
   для сохранённых контактов при разблокированном корректном профиле; отправить
   подготовленный ответ выбранным транспортом. Состояние UI честно различает
   ответ в очереди, доставку, отправку транзакции и chain confirmation.
   Автофинализацию исходящей отправки не включать: подтверждение пользователя и
   привязка к исходной сумме/адресу/комиссии обязательны; изменение этого правила
   требует отдельного решения. Исходящий S2 без подтверждения → needs_review.
4. **Восстановление.** Зафиксировать inbox/outbox, устойчивые переходы,
   идемпотентность и контекст операции. Ошибки записи processing/reply/done не
   игнорировать; повтор одного сообщения или потеря ACK не создаёт второй
   денежный эффект. На этапе анализа проверить обнаруженные во Flint гипотезы:
   повтор `failed/needs_review`, ошибку сохранения флага автообработки, смену
   профиля/lock посреди фоновой операции. Они не являются подтверждёнными багами
   Grin++ и не должны автоматически переноситься как требования переписать Flint.
5. **План выпуска.** Сначала локальная совместимость и безопасная ручная
   операция, затем messenger + opt-in приём; фича может быть выключена без
   нарушения обычного кошелька. До подтверждения — experimental/testnet. Не
   менять версии ноды и не снимать `/W4 /WX` ради интеграции.

### Проверка и критерии готовности слоя

- Unit/контракт: корректные адреса и сеть, шифрование/подписи и границы payload,
  права IPC, изоляция профилей, отсутствие секретов в логах и JS, переключатели
  default-off и ошибки сохранения настроек.
- Транзакции: известный/неизвестный контакт, S1 и S2, изменение суммы/адреса,
  явное подтверждение исходящей операции, отказ устаревшей/неполной сессии;
  queued не считается confirmed.
- Восстановление: повтор доставки с тем же ID, ACK-loss, restart между durable
  переходами и ответом, ошибки записи, смена профиля/lock во время обработки;
  нет второго приёма/подписи/ответа, состояние можно объяснить пользователю.
- Live на **изолированном Floonet**: два независимых тестовых профиля, запуск
  Tor/onion, текст + входящий Slatepack, ответ, finalize/post и реальное chain
  confirmation, рестарт и offline recipient/relay. Зафиксировать версии, SHA,
  транспорт и источники доказательств без seed/паролей/содержимого Slatepack.
  Unit, mock и старые Flint PASS не подменяют этот цикл.
- Реальное Electron UI: вручную открыть окно, проверить переключатель,
  обработку ошибок, lock/unlock и результаты обоих кошельков. До отдельного
  Mainnet решения — никаких реальных средств. Статусы по каждому слою писать
  PASS / FAIL / NOT VERIFIED; не обещать поддержку платформ без их проверки.

**Стоп-условие:** принять минимальный полезный и проверенный слой, не добавляя
новые транспорты/функции только из-за их наличия во Flint. Пасхалка x13 остаётся
последним отдельным этапом API после основной функциональности и доступа.

## G-53 — заключительный этап API: пасхалка «выход x13»

По просьбе владельца добавить пасхалку «выход x13» **последним этапом** работ
над API, после функциональности, совместимости и проверок доступа. Пользователь
считает её важной; этот пункт не заменяет обязательные проверки и не является
доказательством готовности к Mainnet.

**Статус: PLANNED; последняя стадия API, не реализовано.** Содержание ответа
уточнено владельцем:

- Псевдографика с крупной надписью `MW` на зелёном «хакерском» фоне:
  буква `M` чёрная, `W` жёлтая; предусмотреть читаемый бесцветный вариант.
- Надпись `FROM RUSSIA WITH LOVE`: зелёная при наличии ожидаемой встроенной
  метки; при отсутствии метки или невозможности её проверить — красная скобка
  `(` и подпись `MARKER NOT VERIFIED`. Это не проверка оригинальности файла.
  Цвет не должен быть единственным носителем смысла: plain-вывод подписывает
  статус текстом.
- Имена `D.Burkett D.Taurez D. Bear`; ниже — точный текст
  `SIR WE HAVE PEERS!` и число **фактически подключённых** пиров.
- Прогресс четырёх стадий синхронизации, например `1 — 100%`, `2 — 100%`,
  `3 — 100%`, `4 — 44%`; числа в примере иллюстративные и должны вычисляться
  из реальных данных ноды. При реализации определить и документировать связь
  каждой стадии с фактической state machine и источник числителя/знаменателя.
  Недоступный/неприменимый процент показывать как `N/A`, не подставлять 0 или
  100 без основания; не делить на ноль, корректно обрабатывать смену горизонта,
  повторный sync и restart. Не придумывать проценты для фаз без метрик.
- Для цвета выбрать поддерживаемый форматом клиента способ отображения:
  например, ANSI-цвета для терминала при явной поддержке и читаемый вариант без
  escape-кодов для остальных клиентов. JSON-RPC должен оставаться корректным
  JSON; при необходимости вернуть отдельные структурированные числа и текст,
  не смешивая оформление с расчётом. Внешний вид уточняется при реализации.
- Определить точный запрос для «выход x13» и область доступа; не включать его
  в публичную документацию, список методов или каталог API. При этом сохранить
  реализацию в исходниках и автоматических тестах, чтобы она проверялась при
  изменениях. Скрытость не является защитой: использовать обычные для данных
  проверки доступа и авторизацию, не показывать секреты, адреса пиров или другие
  внутренние данные без необходимости. Ответ только для чтения; не добавлять
  обфускацию или криптографию только ради сокрытия пасхалки.

**Лёгкая встроенная метка — согласованная замена внешней проверки:**

В исполняемый код/ресурс включить постоянную метку и при вызове пасхалки
проверять её наличие и значение. Комментарий исходника не подходит: компилятор
не обязан включать его в бинарник. Успех означает только наличие ожидаемой
метки; отсутствие/ошибка — красная `(`. Это простая проверка от случайной потери
метки и подсказка разработчику, а не SHA-256 или доказательство целостности и
происхождения: изменённый бинарник может сохранить метку либо обойти проверку.
Не заявлять `VERIFIED`, «официальная сборка» или факт злого вмешательства.

Если API не отвечает или результат не содержит метку, сам отсутствующий ответ
не способен показать скобку: при наличии отдельного вызывающего клиента он
может отобразить красную `(` с `NO RESPONSE`/`MARKER NOT VERIFIED`; это не
отличает изменённую ноду от остановки, сетевой ошибки или отказа авторизации.
Без отдельного клиента такой индикации при неработающей ноде не будет; не делать
создание внешней утилиты обязательным для этой пасхалки.

Проверить наличие, отсутствие и изменение метки, ошибки проверки и сценарий
отсутствия ответа на стороне вызывающего клиента, если он существует; не влиять
на работу ноды, безопасность API или sync. Публикация хешей и подписанные
манифесты при необходимости могут рассматриваться отдельно для релизов, но не
являются частью и условием приёмки этой пасхалки.

Приёмка: сравнить count с фактическими соединениями и каждый отображённый процент
с источником sync-state; тесты на 0 peers, отсутствие метрик, разные стадии,
рестарт/reorg, права доступа, отсутствие в публичном каталоге и проверку
валидного ответа/цветного и plain-вариантов. Обычные
методы API продолжают работать; пасхалка не влияет на консенсус, синхронизацию
или P2P и реализуется только после основных работ API.
