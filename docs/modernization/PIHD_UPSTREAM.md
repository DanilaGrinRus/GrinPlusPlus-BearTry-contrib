# PIHD_UPSTREAM — как PIHD устроен в ветке `staging`

Статус: справка по внешнему коду, **не план и не задача**. Источник:
`github.com/mimblewimble/grin`, ветка `staging` (HEAD `83ff9af`, 15.10.2026),
PR #3879 «add PIHD header segment protocol» и #3882 «Implement PIHD header sync»
(серия #3835). В тег **v5.5.2 не входит**.

## 1. Где это лежит

| Файл в `staging` | Что там |
|---|---|
| `p2p/src/msg.rs` | типы 29/30, структура `HeaderSegment`, лимиты размеров |
| `p2p/src/types.rs` | `PIHD_HIST = 0b1000_0000`, `PIHD_HEADER_SEGMENT_HEIGHT = 9`, `HeaderSegmentAcceptance` |
| `p2p/src/protocol.rs` | обработка запроса/ответа, обязательный capability |
| `servers/src/common/adapters.rs` | выдача сегментов из header-PMMR, троттлинг |
| `servers/src/grin/sync/header_sync.rs` | клиентская синхронизация, фолбэк |
| `chain/src/pihd_params.rs` | параметры (in-flight, таймауты, cooldown) |

## 2. Проводной формат

| Параметр | Значение |
|---|---|
| `GetHeaderSegment` | тип 29, тело — `SegmentIdentifier` (9 байт) |
| `HeaderSegment` | тип 30, тело: `SegmentIdentifier` + `u16` count + count заголовков |
| Чтение заголовка | `UntrustedBlockHeader` → `into()` (проверка PoW/полей — на стороне получателя) |
| Максимальный размер | `11 + 578 * 512` байт (578 — `max_header_size()`, 512 — `MAX_BLOCK_HEADERS`) |
| Capability | `PIHD_HIST = 0x80`; в `staging` входит в `Capabilities::default()`, то есть рекламируется всеми узлами ветки |
| Сегмент | `height = 9` → ёмкость 512 заголовков; `start = idx * 512 + 1`; `end = min(start + 511, header_head)` |

Существенная деталь: **`idx = 0` начинается с высоты 1** — genesis в сегменты не попадает.

## 3. Серверная сторона

- отвечает только пиру, у которого есть `PIHD_HIST`, иначе `Consumed::None`;
- берёт заголовки из header-PMMR по высотам `start..=end`, обрезая по своему `header_head`;
- троттлинг: **120 запросов на адрес за 60 секунд**, сверх — тихий отказ;
- невалидный ответ на стороне клиента может привести к бану (`HeaderSegmentAcceptance::Ban` → `BadBlockHeader`).

## 4. Клиентская синхронизация

- выбирает пиров: `HEADER_HIST` + `PIHD_HIST`, difficulty и height выше наших; приоритет outbound;
- в полёте: до **8** сегментов, до **2** на пира, до **8** запросов за тик (`pihd_params.rs`);
- таймаут сегмента **20 с**; провал → cooldown **30 с** на пира; **3** провала → `block_peer` (outbound ещё и disconnect);
- **3** таймаута и **120 с** без прогресса → PIHD выключается на **120 с**, откат на legacy header sync;
- порядок: сегменты складываются в `SyncState` и обрабатываются по порядку; опоздавшие/дублирующие отбрасываются;
- режим виден в статусе: `HeaderSyncMode::Pihd | Legacy` (TUI и API статуса).

## 5. Насколько это «в релизе»

`staging` опережает тег `v5.5.2` на **63 коммита** (и отстаёт на 1 — сам релизный).
PIHD влит в `staging` 29.06.2026 (#3879) и 14.07.2026 (#3882), а тег `v5.5.2` собран
09.10.2026 из релизной ветки, куда эта работа не попала: в `v5.5.2` enum сообщений
заканчивается на `KernelSegment = 28`.

Практический вывод: **сеть на v5.5.2 PIHD не требует**, у узлов `staging` остаётся
legacy-фолбэк. PIHD — ускорение первичной загрузки заголовков (параллельные сегменты
с нескольких пиров), а не консенсус.

## 6. Что потребовалось бы для Grin++

| Часть | Оценка |
|---|---|
| Сообщения 29/30 + capability | небольшой слой: сериализация `SegmentIdentifier` + `u16` + заголовки, лимиты как в Rust |
| Сервер | ~150 строк: чтение header-PMMR по диапазону, обязательный capability-гейт, троттлинг |
| Клиент | ~500–700 строк: выбор пиров, in-flight лимиты, упорядоченная обработка, таймауты/cooldown, фолбэк |
| Тесты | `start_height = idx*512+1`, лимит 512, capability-гейт, фолбэк на legacy |

Ловушки, которые видно по коду Rust: смещение `+1` в `start`; проверка непрерывности
и PoW на недоверенных заголовках; привязка к header-PMMR и обработка reorg; не
рекламировать `0x80` до готовности серверной части.
