## 1. G-09 — выдача PIBD-сегментов

**Статус:** PARTIAL/FAIL live serving. Offline-доказательство: 4 тела одного H
(Floonet 3 317 027) валидированы Rust v5.5.2; полный перебор сегментов, переход
между H и живой Rust-клиент — NOT VERIFIED.

### Части

1. **Слияние кандидатного патча и закрепление тестами.**
   - Патч: `GetRawAt` (compaction/bounds), leaf-политика (required → данные,
     optional → prune-aware hash), поиск сохранённого предка по всей
     `family_branch` вместо `branch[0]`.
   - Сверить с текущими незакоммиченными изменениями по смыслу; конфликтные
     места решить вручную, не теряя чужие правки.
   - Тесты: anchor-search (9-листный пример), required leaf без данных →
     `MissingLeaf`, optional compacted leaf → `nullptr`, отсутствие якоря →
     ошибка, а не молчаливый пустой `startPos`.
2. **Согласованный снимок горизонта H.**
   - Заголовок, bitmap и все три PMMR — из одного состояния на всё время
     построения ответа.
   - Узел должен отвечать на **архивный H**, который запрашивает Rust, а не
     только на flushed tip; mismatch — явный отказ, не «похожий» сегмент.
   - `NOT_SYNCING` сам по себе не фиксирует состояние: блок/reorg может изменить
     PMMR между чтением сегмента и companion root.
3. **Полная проверка и live interop.**
   - Перебрать все ID одного H: ожидаемо 7 + 1674 + 1674 + 1638 = 4993 ответа;
     каждый output/rangeproof/kernel валидировать Rust-декодером.
   - Отдельно: последний частичный сегмент, пустой сегмент, последний лист,
     сегмент, требующий подъёма на несколько уровней.
   - Живой Floonet: Rust v5.5.2 клиент сам выбирает H, получает все сегменты у
     C++-пира, завершает PIBD с проверкой корней; фиксировать peer id, H, число
     ответов, отсутствие fallback/примеси других источников, финальный статус.

### Подводные камни

- Нельзя перескакивать предка, содержащего обязательные листья.
- Полностью удалённый сегмент может требовать несколько уровней подъёма.
- Ошибка диска и ожидаемое отсутствие компактированного хеша сейчас могут
  сводиться к одному `nullopt` — различать для диагностики и решения о
  доступности H.
- Capability не должна обещать обслуживание горизонта, которого у узла нет.
- 4 offline-ответа покрывают только выбранные ID — не считать их полной приёмкой.

**Приёмка:** все сегменты H валидны; live Rust-клиент завершил PIBD; ошибки
различимы; G-09 → DONE только после этого.

## 2. G-23 — целостность MMR при открытии

**Статус:** структурная проверка/rebuild DONE (E48); hash/root-ревалидация OPEN.

- Два режима: `structural` (быстрый, по умолчанию) и `hash` (полный, с явным
  сообщением о времени/результате).
- Проверка должна понимать prune list и сохранённые корни: компактированное
  поддерево нельзя проверять как полностью материализованное.
- `Root(size)` для исторического размера не должен читать чужой узел через
  shifted index: «исторический корень недоступен» — до использования в
  проверке/rewind.
- Отказ проверки не удаляет и не переписывает данные: диагностика, копия,
  восстановление — отдельные действия.
- Output, rangeproof, kernel, bitmap и заголовок проверять на одном
  зафиксированном состоянии.

**Приёмка:** подмена байта в копии БД ловится с точной позицией; чистое состояние
проходит в согласованный бюджет; повторный запуск идемпотентен; повреждение не
приводит к автопочинке.

## 3. G-53 и остаток API — KernelIndex, get_kernel, блокировки

**Статус:** PARTIAL. Часть pagination/snapshot API уже портирована (E60–E68),

- **KernelIndex:** привязать к chain state; после reorg, отката, импорта
  TxHashSet и рестарта не отдавать результат старой ветви. Частичный/повреждённый

- **Пагинация:** пустые диапазоны, последний элемент, переполнение индексов,

- **Блокировки:** документировать порядок; проверить ABBA/self-lock; параллельные

- **GUI ↔ API:** отдельно проверить стык GUI с защищённым `/v1/shutdown` живым
  тестом текущих GUI и ноды.

**Приёмка:** контрактные тесты на фикстурах, live RPC на изолированной Floonet,
отсутствие старых kernel-ответов после reorg/рестарта.

## 6. Staging, восстановление и reorg

- Прерывать процесс до/после каждого шага записи, fsync, rename, обновления
  маркера; после рестарта должна выбираться одна согласованная версия.
- Нехватка места: при записи, создании backup, перемещении и восстановлении.
- RocksDB: проверять восстановимость копии в отдельном каталоге; успешное
  копирование файлов не подтверждает согласованность БД.
- Reorg во время загрузки сегментов инвалидирует прогресс, привязанный к старому
  H; повторная загрузка не должна смешивать сегменты разных горизонтов.
- Существующие recovery-каталоги и резервные копии сохранять до отдельного
  подтверждённого решения.

**Приёмка:** инъекции сбоев + рестарт; одна версия состояния; нет потери данных
без диагностики.

## 7. G-49 — ускорение проверки rangeproof

**Статус:** OPEN (после функциональной проверки текущего пути).

- Сначала измерить время/ресурсы на одном снимке; каждый вариант сравнивать с
  последовательной проверкой.
- Resume привязывать не к номеру proof, а к H/block hash, корням, размеру PMMR,
  версии правил и подтверждённому прогрессу.
- Параллельная проверка: ошибка любого worker завершает общую проверку отказом;
  нельзя продолжать активацию по частичному результату.
- Проверить память/число потоков на слабой машине; ускорение на одном CPU не
  гарантирует улучшение везде.
- Заявленные сроки — цель для замера, пока нет повторяемого результата.

**Приёмка:** ≤5 мин на том же state, те же roots/sums, RSS в бюджете, resume не
пересчитывает пройденное.
