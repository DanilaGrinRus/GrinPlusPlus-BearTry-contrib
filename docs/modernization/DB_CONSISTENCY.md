# DB_CONSISTENCY — рассинхронизация header MMR и chain-файлов

Статус: **обнаружено и воспроизведено**; загрузочная починка реализована
(`0331ea1`, unit-тесты 4 кейса); **исправление в пути записи (формирование БД)
не сделано** — это следующая задача после основной (`GAP_MATRIX` G-46/G-48).
Основание: аварийное падение `pp-g38` (31.10.2026, 15:28) и последующие
`0xC0000005` при старте, воспроизведение, разбор кода хранилищ.

## 1. Что произошло

1. `pp-g38` (свежий HOME, синхронизация заголовков с `204.168.202.205`) был
   **аварийно завершён во время записи заголовков** (около 3.29 млн из 3.32 млн).
   В логе последняя строка — обычная обработка `Headers`, без исключения.
2. Перезапуск того же HOME падал через ~10 с с `0xC0000005` (access violation),
   без stderr и без записи в Windows Application log (WER-дампы недоступны:
   нет прав администратора, LocalDumps в HKLM запрещён).
3. **Удаление каталога `NODE`** (только тестовый `.tmp/interop/pp-g38`) сделало
   старт снова рабочим → проблема в **сохранённом состоянии**, не в бинаре.
4. До удаления наблюдалось: `NODE/CHAIN/header_mmr.bin` ~212 МБ,
   `candidate.chain` ~1.46 МБ, `confirmed.chain` 32 байта (только genesis).
   Здоровый срез: `candidate.chain` = 45 697 записей × 32 Б, MMR = 91 388
   хешей; `2·45697 − popcount(45697) = 91388` — согласовано.

## 2. Причина (код)

Chain-состояние хранится в **трёх независимых append-only файлах**:

| Файл | Класс | Запись | Единица |
|---|---|---|---|
| `CHAIN/header_mmr.bin` | `HashFile` | `MMRHashUtil::AddHashes` → `Commit()` | 32-байтовый хеш узла MMR |
| `CHAIN/candidate.chain` | `DataFile<32>` (`Chain`) | `Chain::AddBlock` → `ChainStore::Commit()` | хеш заголовка на высоту |
| `CHAIN/confirmed.chain` | `DataFile<32>` | то же | то же |

* `HeaderMMR::AddHeader`/`Commit` (`src/PMMR/HeaderMMRImpl.cpp`) фиксирует
  листья MMR; `Chain::Commit`/`ChainStore::Commit` (`src/BlockChain/Chain.cpp`,
  `ChainStore.cpp`) фиксируют индексы отдельно.
* Общего журнала/транзакции нет: жёсткий kill между коммитами оставляет
  `header_mmr.bin` и `candidate.chain` на **разных высотах**.
* При загрузке `BlockChain::Create` (`src/BlockChain/BlockChainImpl.cpp`) до
  сих пор **не сверял** число листьев MMR с высотой candidate chain (это и был
  открытый пункт GAP G-23 «re-validate on load (TODO)»). Если chain-индекс
  уходит вперёд MMR, чтение заголовка на высоту за пределами MMR приводило к
  выходу за файл/нулевому указателю → `0xC0000005`; если MMR впереди — часть
  заголовков «висела» без индекса.
* `confirmed.chain` (genesis) в норме может быть пустым относительно
  candidate; опасен только случай `confirmed > candidate`.

## 3. Что уже сделано (загрузочная починка, `0331ea1`)

* `IHeaderMMR::GetLeafCount()` — число листьев MMR (по размеру `HashFile`).
* `ChainConsistency::ComputeChainRepair(mmrLeaves, candidateEntries,
  confirmedEntries)` — чистая функция, возвращает план: какие хранилища и до
  какого числа записей откатить; приоритет — chain-индекс, лишние листья MMR
  отбрасываются, недостающие восстанавливаются откатом цепочки.
* `BlockChain::Create` **до** `ChainState::Create` применяет план:
  `HeaderMMR::Rewind`/`Commit` либо `Chain::Rewind`/`ChainStore::Commit`, пишет
  `WARNING "Chain stores inconsistent … repairing to N entries"` и
  `"Chain stores repaired."`.
* Дополнительно закрыт NULL-deref в обработчике `Ping`
  (`MessageProcessor.cpp`): при отсутствии confirmed-tip теперь пишется
  `WARNING "Cannot answer Ping: no confirmed tip header."` вместо падения.
* Тесты: `Test_ChainConsistency` — 4 кейса (согласовано; MMR впереди; chain
  впереди; confirmed впереди candidate); полный набор **150 кейсов /
  1661 проверка PASS**.

## 4. Что необходимо поправить **при формировании БД** (следующая задача)

Загрузочная починка маскирует рассинхронизацию: после аварии теряется часть
уже скачанных заголовков, а инвариант держится только на эвристике. Нужно
сделать запись **краш-согласованной**:

1. **Единая точка фиксации.** После записи MMR и chain-индексов атомарно
   обновлять один checkpoint-файл (`mmr_leaves`, `candidate_height`,
   `confirmed_height`, хеш/CRC, версия), например временный файл + `rename`
   (как `PibdActivation`) либо RocksDB-батч. При загрузке обрезать все три
   хранилища ровно до checkpoint.
2. **Порядок коммитов и инвариант.** Никогда не коммитить chain-индекс
   впереди MMR; предпочтительный порядок: MMR → checkpoint → chain (или
   наоборот) с явно задокументированным правилом восстановления. Инвариант:
   `candidate_entries − 1 ≤ mmr_leaves` и `confirmed_entries ≤ candidate_entries`
   проверять на каждом коммите.
3. **Формат/целостность.** Для append-only файлов хранить длину/поколение и
   `fsync` (сейчас `Commit` не даёт гарантий порядка на уровне ОС); при
   загрузке проверять, что размеры кратны записи и последняя запись целая.
4. **Crash-тесты с инъекцией.** Добавить шов «точка сбоя» между коммитами и
   тест: убить процесс перед/после каждого `Commit` и проверить, что старт
   восстанавливает состояние без потери подтверждённых данных (новая высота
   ≤ последнего checkpoint; никаких AV).
5. **Ревалидация MMR (G-23).** Дополнительно к счётчикам проверять корень
   MMR/непрерывность хешей (или контрольную сумму диапазона) при загрузке;
   то же для PMMR txhashset. Это дороже, поэтому — как отдельная опция
   (`--validate-on-load`) или периодическая проверка.
6. **Диагностика.** При починке сохранять копию «битых» файлов (или
   смещений/размеров) в `NODE/recovery-<timestamp>/`, писать причину в лог и
   отдавать в `/v1/status` счётчик `db_repaired`.

## 5. Воспроизведение

* Симптом: старт завершается `0xC0000005` в течение ~10 с после подключения
  пира; лог обрывается на `Headers`/`ProcessMessage` без исключения.
* Проверка состояния: `NODE/CHAIN/header_mmr.bin` размер / 32 = число узлов
  MMR; `NODE/CHAIN/candidate.chain` размер / 32 = число записей chain;
  для N записей chain ожидается `2N − popcount(N)` узлов MMR.
* Контролируемый тест (после сборки бинаря с починкой): скопировать HOME,
  обрезать `candidate.chain` (или `header_mmr.bin`) на 32·k байт, запустить
  узел с отдельными портами и убедиться, что в логе есть
  `Chain stores inconsistent … repairing`, а узел продолжает синхронизацию без
  падения.

## 6. Ограничения текущего состояния

* Починка выполняется только при старте и только по **количеству** записей;
  побайтовая целостность/хеши не проверяются (G-23 остаётся частично
  открытым).
* Порядок `fsync` между файлами по-прежнему не контролируется; при потере
  питания возможна потеря уже «закоммиченных» записей.
* Живой crash-тест на бинаре с починкой ещё не прогнан (unit PASS; сценарий
  описан в §5) — это доказательство нужно приложить к следующей итерации.
